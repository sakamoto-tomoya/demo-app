# Dify ワークフロー／チャットアプリ用プロンプト追記

修理アシスト（`/api/dify/repair-assist`）は、サーバー側でナレッジを抽出してから `request_text` に埋め込みます。  
Dify 側の**システムプロンプト**（または「指示」ブロック）に、次を**追記**してください。

---

## 出力を「推定部品名＋在庫のみ」に絞る（遅延・ハルシネ・ノイズ対策）

### ワークフロー構成の目安

| 問題 | 対策 |
|------|------|
| ① 遅い | **LLM ノードは1つ**に集約。ナレッジ検索ノードは**無効**（アプリが既に `request_text` に参照文を入れているため二重検索になる）。HTTP（部品検索）が必要なら **LLM の直前に1回だけ**。 |
| ② 余計な部品候補 | プロンプトで「**ナレッジに【使用部品名】等として明示されたものだけ**」「**一般論の部品列挙禁止**」。必要なら LLM の前に **コードノード**で `request_text` から `【使用部品品番】` 行だけ抽出し、LLM にはその行＋HTTP結果だけ渡す。 |
| ③④⑤ 注意書き・冗長・ハルシネ | **出力形式を JSON 固定**（下記テンプレ）。**前置き・箇条書きの説明・免責は禁止**と明記。根拠外の推測禁止。 |

### 在庫状況について

本リポジトリの Turso `parts` テーブルには **在庫専用列はない**（`note` 等で運用するか、別システム連携が必要）。Dify の **HTTP ノード**で在庫APIや別DBを叩く場合は、**そのレスポンスに書かれた在庫だけ**を `stock_status` に写す。データが無いときは `在庫: 未連携` のように **固定文言1行**にし、LLM に推測させない。

### 最終 LLM ノード用・システムプロンプト（コピー用）

```
あなたは出力生成器です。会話は禁止。前置き・謝罪・注意事項・免責・補足説明は一切書かない。

入力:
- request_text: アプリが付与したナレッジ抜粋と依頼文（この中の【型式】【症状】【使用部品品番】【使用部品名】等のみが根拠）
- （任意）parts_tool_result: HTTP部品検索APIのJSON本文

ルール:
1. estimated_part_name: ナレッジ本文に明示された使用部品（部品名）のみ。該当が複数あるときはナレッジ上で症状・型式に最も近い1件に絞る。ナレッジに部品名が無い場合は null（空文字ではなく JSON の null）。一般知識や推測で部品名を補わない。
2. stock_status: parts_tool_result に在庫情報がある場合のみその文字列を要約（1行）。無い場合は「在庫: 未連携」または null のいずれかに統一（運用で決めてよい）。在庫を推測しない。
3. 上記2キー以外のキーを出力しない。マークダウンや箇条書きを使わない。

出力は次の JSON のみ（説明文なし）:
{"estimated_part_name": string | null, "stock_status": string | null}
```

### 変数の渡し方（ワークフロー入力）

アプリは `request_text`・`manufacturer`・`model_name` を渡しています。LLM には **`request_text` と（設定していれば）部品検索HTTPの結果**だけを渡すとノイズが減ります。

## 速度（モデル）

チャットアプリの**モデル設定**で、レイテンシ優先の軽量モデルに切り替えてください。  
`/chat-messages` API からモデル名を上書きする仕様ではないため、**Dify コンソール上の設定**が必要です。

---

## 二重検索の回避

アプリに**ナレッジ検索ノード**が有効なままだと、アプリ側の検索と API が渡す `query` 内テキストが二重になり、遅延やノイズの原因になります。  
修理アシスト用アプリでは、次のいずれかを推奨します。

- ナレッジ検索ノードをオフにし、`request_text` に含まれる参照テキストのみを使う  
- またはワークフローで「API から渡す変数」のみを LLM に渡す

---

## 環境変数（サーバー）

| 変数 | 用途 |
|------|------|
| `DIFY_APP_API_KEY` | チャット（repair-assist の `chat-messages`） |
| `DIFY_KNOWLEDGE_API_KEY` | データセット retrieve |
| `DIFY_KNOWLEDGE_DATASET_ID` | Web完了登録が保存されるナレッジ（retrieve 対象の1つ目） |
| `DIFY_REPAIR_HISTORY_DATASET_ID` | 修理履歴ナレッジ（retrieve 対象の2つ目） |
| `DIFY_REPAIR_ASSIST_DATASET_ID` / `DIFY_DATASET_ID` | 上記2つがどちらも未設定のときのフォールバック |

repair-assist の `inputs.dataset_ids` には、`DIFY_KNOWLEDGE_DATASET_ID` と `DIFY_REPAIR_HISTORY_DATASET_ID` の**両方**（設定されているもの）を JSON 配列文字列で渡します。ワークフロー側で変数名 `dataset_ids`（または `dataset_ids` をパースしてナレッジノードに渡す）を定義してください。

`DIFY_BASE_URL` は通常 `https://api.dify.ai/v1`（末尾スラッシュなし可）。

## サーバー側 retrieve（repair-assist）

- **データセットごと**に次を実行し、最後に全結果をスコアでマージして上位 **3** 件にまとめる。
1. 症状クエリと `【型式】{正規化型式}` クエリを **並列** で `POST /datasets/{id}/retrieve`（`semantic_search`, `top_k` 12, スコアしきい値 **0.7**）。
2. 結果をマージし、チャンク本文の `【型式】` 行（またはレガシー行一致）で **型式完全一致** のものだけ残す。
3. データセット内で 0件のときのみ、しきい値なしで再検索 → 同じ型式フィルタ。

Dify のナレッジ API には **レート制限** があるため、短時間に連打すると 400 になる場合があります。
