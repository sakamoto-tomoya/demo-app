# 新規案件・チャット質問機能の受付情報ベース事前検索 変更サマリ

## 1. 現在の送信文（修正前）と修正後の送信文

### 修正前（完了案件前提）
- **API に渡していたもの**: `inputs` に `case_search_text`, `case_model`, `case_inquiry`, `case_work_detail`, `case_note` などを個別に渡し、`query` にはボタン文言のみ（例: 「この案件の解決方法を教えて」「想定原因を教えて」「交換候補部品を教えて」）をそのまま送信。
- **送信例**:  
  - query: `この案件の解決方法を教えて`  
  - inputs: case_model=型式, case_inquiry=内容, case_work_detail=社内連絡 など  
- 本文は Dify 側のプロンプト／変数に依存しており、受付情報を「1本の検索文」としてまとめていなかった。

### 修正後（受付情報ベース・事前検索用）
送信する **query** を、以下の1本の本文に統一。

```
案件の事前検索をしてください。

【型式名】
{型式名 または （未入力）}

【お申し出型式名】
{お申し出型式名 または （未入力）}

【ガス種】
{ガス種 または （未入力）}

【内容】
{内容（症状・使用年数・請求先等） または （未入力）}

この受付情報に近い過去の完了案件を参考にして、
1. 想定原因
2. 事前確認ポイント
3. 改善方法の候補
4. 交換候補部品
を回答してください。

類似案件が少ない場合でも、型式名と内容から一般的に考えられる候補を簡潔に提示してください。

{意図別の一文}
```

**意図別の一文（ボタンごと）**
- この案件の解決方法を教えて → `上記について、解決方法・改善方法を中心に回答してください。`
- 想定原因を教えて → `上記について、想定原因を中心に回答してください。`
- 交換候補部品を教えて → `上記について、交換候補部品を中心に回答してください。`

## 2. 修正したファイル一覧

| ファイル | 変更内容 |
|----------|----------|
| `src/lib/dify-chat-query.ts` | **新規**。`buildReceptionQueryText()` と `DifyChatQueryIntent` を定義。受付情報（型式名・お申し出型式名・ガス種・内容）と意図から上記の送信本文を組み立て。 |

| ボタン | query_intent | 送信本文の最後に付く一文 |

## 4. 実際の送信ログ例

### ブラウザ（開発者ツールコンソール）
チャットでいずれかのボタンを押した直後:

```
[CaseForm] 送信直前の最終本文 (Dify chat):
=== Dify chat query (reception) start ===
案件の事前検索をしてください。

【型式名】
FHE2421SAWL

【お申し出型式名】
FHE2421SAWL

【ガス種】
都市ガス

【内容】
お湯が出ない。使用年数10年。

この受付情報に近い過去の完了案件を参考にして、
1. 想定原因
2. 事前確認ポイント
3. 改善方法の候補
4. 交換候補部品
を回答してください。

類似案件が少ない場合でも、型式名と内容から一般的に考えられる候補を簡潔に提示してください。

上記について、想定原因を中心に回答してください。
=== Dify chat query (reception) end ===
```

### サーバー（ターミナル / ログ）
API が Dify に送る直前に同じ内容を出力:

```
[dify] 送信直前の最終本文:
=== Dify chat query (reception) start ===
（上記と同様の本文）
=== Dify chat query (reception) end ===
```

## 5. Dify 側の設定について

- 「情報不足です」で終わらず、型式名・内容から一般的な候補（想定原因・事前確認・改善方法・交換候補部品）を返すには、Dify のワークフロー／プロンプトで「類似案件が少ない場合でも、型式名と内容から一般的に考えられる候補を簡潔に提示する」旨を指示しておく必要があります。
- 今回の変更は **送信する query 本文** を「受付情報ベースの1本の検索文＋意図」に統一しただけです。Dify 側のプロンプトやナレッジ検索設定は既存のままでも動作しますが、上記の振る舞いを期待する場合は Dify 上でプロンプトの追記・調整をしてください。
